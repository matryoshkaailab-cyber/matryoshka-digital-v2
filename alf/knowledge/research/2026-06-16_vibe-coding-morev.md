## 2. Главная идея

«Скучный, системный» подход к vibe-coding вместо хайпа вокруг топ-моделей (Claude, OpenAI). Фокус на **воспроизводимом сетапе**, который работает на дешёвых китайских моделях (MiniMax M3, Kimi K2.6, Qwen, GLM, DeepSeek) и **не зависит от зарубежных платформ**.

> Аналогия автора: «Можно годами ездить на машине и не знать, как устроен двигатель. Я хочу знать».

## 3. Почему автор НЕ использует топовые модели

### Причина №1 (техническая)
- Топовые модели (Claude, GPT) настолько умные, что разработчик становится «оператором кнопки».
- Разработчик теряет понимание архитектуры, движка, процессов.
- Топ-модель рентабельна только тем, кто уже умеет конвертировать код в деньги (5% от з/п → ускорение в 3-4×).
- Начинающим вредно: они не смогут отделить «магию» от реальной инженерии.

### Причина №2 (политическая / прагматичная)
- OpenAI отклонил оплату белорусской картой.
- Приходилось покупать GPT+ через реселлеров, левые карты, VPN.
- Принципиальный отказ от проприетарных западных моделей.

**Вывод автора**: начинать знакомство лучше с околотоповых/китайских моделей, постепенно понижая уровень, чтобы понимать, что ты делаешь.

## 4. Технологический стек

### Основной агент: **pi.dev**
- Пакет: `@earendil-works/pi-coding-agent`
- Команда: `pi`
- Требуется: Node.js 20+ (рекомендуется LTS 22 или 24)
- Установка: `npm install -g --ignore-scripts @earendil-works/pi-coding-agent`
- Автор утверждает, что pi.dev **заменил ему** OpenClo(?) и собственного бота Hermes
- Концепция: из коробки почти ничего не умеет (только чат + редактирование файлов) — всё остальное через MCP

### MCP-серверы (всего 2!)
1. **chrome-devtools-mcp** — управление Chrome через CDP
   - Запуск Chrome: `chrome.exe --profile-directory="Profile 2" --remote-debugging-port=9222 --user-data-dir="C:\temp\chrome-debug\1"`
   - Подключение: `"--browser-url=http://127.0.0.1:9222"`
   - Профиль сохраняет авторизации (можно залогиниться руками 1 раз)
2. **SSH MCP** — для деплоя на сервер

### Пакеты pi.dev
- `pi-mcp-adapter` — для регистрации MCP-серверов (https://pi.dev/packages/pi-mcp-adapter)
- `pi-subagents` — для запуска субагентов (https://pi.dev/packages/pi-subagents)

### Структура mcp.json
Расположение: `~/.pagent/mcp.json` (папка `pagent` в домашней директории пользователя)

## 6. Ключевые принципы методологии

### 6.1. AGENTS.md как контрактор
- **Основной файл проекта для агента**: `agents.md` (в корне) + `AGENTS.md` (дополнительный)
- Содержит: архитектуру, команды запуска, переменные окружения, API endpoints, описание субагентов, важные правила
- **Агент сам его пишет**, человек только верифицирует
- В подпапках (например `apps/backend/`) могут быть свои `AGENTS.md` для сужения контекста

### 6.2. Треугольник стабильности: **Фича → E2E-тест → Документация**
1. Реализовали фичу
2. Написали E2E-тест (Playwright через CDP, `workers=1`)
3. Обновили документацию

Это гарантия стабильности при длительной разработке.

### 6.3. Логирование через log-runner
- Команды: `npm run dev:backend:log` / `dev:frontend:log`
- PID-файлы (`backend.pid`) — для перезапуска
- Логи: `logs/backend.log`
- **Агент сам читает логи и чинит ошибки** — пример из видео: намеренно сломанный код, агент сам нашёл опечатку, исправил и перепроверил

### 6.4. Папка ТЗ (спецификации)
Для сложных задач — двухфазный workflow:
1. Фаза сбора: «Собери всю информацию о проблеме в файл ТЗ» → агент пишет spec
2. Фаза решения: «Перезапусти сессию с пустым контекстом и реши по ТЗ»
- Позволяет **переключать модели** между фазами (например, если MiniMax не справился → GPT 5.5 по токенам → локальный Qwen)

### 6.5. Субагенты против «утечки контекста»
- Главная проблема: при прямом выполнении UI-задач в основном чате браузер через Chrome DevTools MCP выбрасывает **гигантский технический лог** (DOM, сетевые запросы, ошибки консоли)
- Даже с 1M контекстом модель «начинает плыть» — теряет важную информацию в шуме
- Решение: субагенты через `pi-subagents` — они изолируют технический контекст, возвращают только результат

## 7. Практические кейсы из видео

### 7.1. Исправление бага (48:22)
- Баг: клик по аватару в header уводил на нерабочую страницу
- Промт: «В хедере при нажатии на айди админ переходит на нерабочую страницу. Пусть переходит в админ-панель. После исправления проверь сам через MCP браузера и напиши e2e тест»
- Результат: агент исправил + сам проверил через браузер + написал E2E-тест
- Модель: **MiniMax M3** (локально Qwen 27B тоже справился бы, но медленнее)

### 7.2. Удаление пользователя (51:26) — кейс «агент умнее ожидаемого»
- Задача: реализовать удаление пользователей в админке
- Запрос ТЗ → агент изучил проект и **нашёл, что функционал УЖЕ есть**
- Дополнительно нашёл баги:
  - Backend не блокирует самоудаление (только UI)
  - Нет защиты удаления последнего админа
  - Любой залогиненный мог вызвать delete-метод
  - Модальный диалог не нативный
  - Нет фидбека по каскадному удалению
  - Нет теста на удаление
- **Урок**: при работе с агентом обязательно верифицировать его находки

### 7.3. Система мероприятий с нуля (55:58)
- Промт: «Сделать систему управления списком мероприятий. В админ-панели блок `/admin/events`, где админ заводит мероприятия (название, описание, ссылка, дата). В пользовательской части страница `/events` с фильтром по дате»
- Агент сам:
  - Создал модель БД
  - Реализовал CRUD
  - Авторизовался через UI, добыл токен, дёрнул API, проверил данные
  - Запустил Playwright
  - Идёт по пути наименьшего сопротивления (UI → токен → API)

### 7.4. Деплой на чистый сервер (65:17)
- Хостер: **Aeza-style** (HHSHP), дешёвые сервера от 200₽/мес
- В Германии выдача может идти днями; в Финляндии — минуты
- Двухфазная подготовка сервера (`deploy/prepare/`):
  - `prepare-server-1.sh`: swap 2G, создание пользователя `vibecoder`, сохранение хэша пароля
  - `prepare-server-2.sh`: установка `sudo/ufw/fail2ban/openssh-server`, смена SSH-порта на **2091**, отключение root-входа, UFW (default deny), fail2ban (5 попыток / 10 мин / бан 1 час)
- Сам деплой: через **SSH MCP** агент сам:
  - `git clone` репозитория
  - `npm install`
  - Копирование `.env.example` → `.env` с подстановкой паролей
  - `npm run build`
  - systemd unit `/etc/systemd/system/vibe-setup-ui.service`
  - Открытие порта 3000 в UFW
  - Проверка `curl http://localhost:3000/api/users/count`

## 9. Критический анализ

### Сильные стороны
1. **Воспроизводимость**: всё задокументировано, нет «магии под капотом»
2. **Изоляция от санкций**: работает из РФ/РБ без VPN
3. **Дешевизна**: 1500₽/мес против $200 за Claude Max
4. **Стабильность через E2E**: реальная инженерная дисциплина, а не «авось сработает»
5. **Шаблон**: repo можно склонировать и сразу работать
6. **readme-for-agents.md**: блестящая идея — отдельный файл-инструкция для ИИ-агента

### Слабые места / риски
1. **Деплой без Docker** в публичной версии — больше рискую с зависимостями ОС
2. **Docker-версия за paywall** (Boosty) — противоречит заявленной «открытости»
3. **Субъективная антизападная риторика** как «причина» не использовать топовые модели маскирует реальный барьер (отсутствие удобной оплаты)
4. **Слабая модель = больше возни**: автор сам признаёт, что иногда приходится докупать GPT 5.5
5. **Pi.dev малоизвестен** vs Claude Code / Cursor — экосистема меньше, рискованнее ставка
6. **Локальный сетап на 4090 48GB** недоступен 99% аудитории — противоречит заявлению «для новичков»
7. **Автор — одновременно продавец моделей и преподаватель** (ai.wormsoft.ru) — конфликт интереса

### Спорные утверждения
- «Топовые модели вредны для понимания» — спорно: Claude Opus с subagent临床上 ускоряет обучение, а не тормозит
- «Китайские модели можно использовать без оглядки на топовые» — на сложных задачах (большая архитектура) разрыв 3-5× в качестве реален

## 10. Применимость к MATRYOSHKA DIGITAL

### Что можно заимствовать
1. **Папка ТЗ workflow** — у нас HERMES уже пытается делать нечто подобное через `.hermes_task.json`, но без двухфазности «spec → restart». Можно ввести явный механизм.
2. **Треугольник Фича → E2E → Документация** — у ALEX сейчас мало E2E-тестов. Это серьёзная дыра.
3. **readme-for-agents.md** — отдельный файл для агентов в репо matryoshka-repo. Сейчас AGENTS.md смешивает человеко-читаемое и агенто-читаемое.
4. **log-runner с PID-файлами** — решает проблему «как агенту понять, что сервис упал»
5. **Изоляция субагентов для браузерных задач** — Puppeteer MCP в ALEX сбрасывает в контекст огромный DOM; можно вынести в subagent

### Отличия от нашего сетапа
- У нас основной канал — **opencode**, не pi.dev
- У нас уже есть **ACP-мост** и **alex_bridge.py**
- У нас **HERMES как дирижёр** + **ALEX как руки** — двухуровневая схема, у Морева один агент
- Мы используем в основном **Qwen, Claude (через Zen), DeepSeek, GLM** — близко к его набору

### Прямые заимствования в `.opencode/`
- Создать **playwright E2E-папку** для matryoshka-repo с шаблонами тестов
- Создать **templates/specs/** с примером ТЗ-файла
- Дополнить **AGENTS.md** разделом «как агенту чинить упавший backend» (по образцу log-runner)
- Завести **`opencode-commands/newtask`**, реализующий двухфазный spec→restart workflow

## 12. Резюме в одном абзаце

Антон Морев показывает **полностью рабочий, воспроизводимый сетап для vibe-coding** на pi.dev + NestJS/Vue + Playwright с MCP-обвязкой (Chrome DevTools + SSH). Слабое место — публичная версия без Docker за paywall, но в остальном это **одна из лучших русскоязычных методологий по vibe-coding на сегодня**.
