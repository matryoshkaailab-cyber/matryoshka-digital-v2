# DATALINK PRO — ДИАГНОЗ И ПЛАН ИСПРАВЛЕНИЯ
## Текущие проблемы и решения по состоянию на 30 апреля 2026

**Сервер:** 85.137.166.209 (Чехия, SmartApe, Ubuntu 24.04)  
**Текущий стек:** VLESS + Reality, Xray напрямую на портах 443/2053/12345  
**Статус:** Работает частично — YouTube не работает, мобильный падает после 21:00

## ЧАСТЬ 1: ДИАГНОЗ — ЧЕТЫРЕ ПРОБЛЕМЫ

### Проблема 1 — YouTube не работает (КРИТИЧНО, решается за 5 минут)

**Причина:** Ошибка в routing. YouTube частично раздаёт контент через российские CDN-серверы. Правило `geoip:ru → direct` перехватывает эти запросы и отправляет их напрямую без VPN. YouTube получает российский IP пользователя и блокирует видео.

**Это не проблема протокола. Это неправильный routing.**

---

### Проблема 2 — После 21:00 мобильный не работает (ТСПУ, частично решаемо)

**Причина:** ТСПУ вечером переключается в более агрессивный режим фильтрации. Днём не хватает вычислительных ресурсов на глубокую инспекцию — вечером нагрузка меньше и DPI работает жёстче. Это системная проблема, подтверждённая сотнями пользователей на форумах с одинаковой картиной: работает до вечера, после 21:00 мобильный падает.

**Дополнительный фактор:** SNI `www.microsoft.com` — это плохой выбор. Это один из самых наблюдаемых ТСПУ доменов. Проверка соответствия IP+SNI паллит такие конфиги первыми именно на мобильных операторах.

---

### Проблема 3 — SNI www.microsoft.com (КРИТИЧНО, сменить немедленно)

**Причина:** ТСПУ мониторит крупные популярные домены особенно внимательно. Microsoft.com — в числе первых под наблюдением. На мобильных операторах (Билайн, МТС) проверка IP+SNI для таких доменов работает агрессивнее всего.

---

### Проблема 4 — Xray без Nginx (уязвимость к активному зондированию)

**Причина:** ТСПУ использует активное зондирование — сам стучится на подозрительные серверы и анализирует ответы. Если Xray отвечает напрямую на 443 без веб-сервера перед ним — паттерн ответа отличается от обычного HTTPS-сервера. IP попадает в базу для усиленного мониторинга.

С Nginx перед Xray: сканер получает ответ обычного веб-сервера — нет подозрений. Без Nginx: Xray обрабатывает все соединения включая сканеры — выше риск занесения IP в базу ТСПУ.

## ЧАСТЬ 2: ИСПРАВЛЕНИЯ — ПО ПРИОРИТЕТАМ

### Исправление 1 — Routing (СДЕЛАТЬ ПРЯМО СЕЙЧАС, 5 минут)

Открыть `/usr/local/etc/xray/config.json` и заменить секцию `routing` на следующую:

```json
"routing": {
  "domainStrategy": "IPIfNonMatch",
  "rules": [
    {
      "type": "field",
      "domain": [
        "youtube.com",
        "googlevideo.com",
        "ytimg.com",
        "ggpht.com",
        "gvt1.com",
        "gvt2.com"
      ],
      "outboundTag": "proxy"
    },
    {
      "type": "field",
      "domain": [
        "instagram.com",
        "cdninstagram.com",
        "fbcdn.net",
        "facebook.com"
      ],
      "outboundTag": "proxy"
    },
    {
      "type": "field",
      "ip": ["geoip:private"],
      "outboundTag": "direct"
    },
    {
      "type": "field",
      "domain": ["geosite:ru"],
      "outboundTag": "direct"
    },
    {
      "type": "field",
      "ip": ["geoip:ru", "geoip:by", "geoip:kz"],
      "outboundTag": "direct"
    },
    {
      "type": "field",
      "domain": ["geosite:category-ads-all"],
      "outboundTag": "block"
    },
    {
      "type": "field",
      "protocol": ["bittorrent"],
      "outboundTag": "block"
    },
    {
      "type": "field",
      "network": "tcp,udp",
      "outboundTag": "proxy"
    }
  ]
}
```

**Почему это работает:** правила применяются сверху вниз, первое совпадение выигрывает. YouTube и Instagram принудительно идут через proxy ДО того как сработает правило geoip:ru. Это решает проблему с заблокированными видео.

После изменения:
```bash
xray run -test -config /usr/local/etc/xray/config.json
# Ожидаемый вывод: Configuration OK

systemctl restart xray
```

### Исправление 2 — Смена SNI-донора (СДЕЛАТЬ СЕГОДНЯ, 10 минут)

В `/usr/local/etc/xray/config.json` в секции `realitySettings` заменить:
```json
"dest": "www.microsoft.com:443",
"serverNames": ["www.microsoft.com"]
```

На:
```json
"dest": "www.speedtest.net:443",
"serverNames": ["www.speedtest.net"]
```

**Перед сменой проверить кандидата:**
```bash
# Проверить TLS 1.3
curl -svo /dev/null https://www.speedtest.net 2>&1 | grep "TLSv"
# Нужно: TLSv1.3

# Проверить нет ли редиректа
curl -I https://www.speedtest.net 2>/dev/null | head -3
# Нужно: HTTP/2 200

# Проверить что не за Cloudflare
curl -sI https://www.speedtest.net | grep "CF-RAY"
# Нужно: пустой ответ
```

После смены донора — перегенерировать ключи Reality и перевыпустить конфиги всем пользователям:
```bash
xray x25519
# Сохранить новые Private key и Public key
# Обновить конфиг, перезапустить Xray
# Обновить клиентские ссылки у всех пользователей
```

### Исправление 3 — Вернуть Nginx как reverse proxy (СДЕЛАТЬ СЕГОДНЯ)

Nginx защищает от активного зондирования ТСПУ. Установить и настроить:

```bash
apt install -y nginx
```

Конфиг `/etc/nginx/nginx.conf`:

```nginx
user www-data;
worker_processes auto;
pid /run/nginx.pid;

events {
    worker_connections 1024;
}

stream {
    server {
        listen 443;
        proxy_pass 127.0.0.1:10443;
        proxy_timeout 600s;
        proxy_connect_timeout 5s;
    }
}

http {
    server {
        listen 80;
        server_name _;
        return 301 https://$host$request_uri;
    }

    server {
        listen 8080;
        location / {
            return 200 'DataLink Technologies';
            add_header Content-Type text/plain;
            add_header Server nginx;
        }
    }
}
```

Переконфигурировать Xray: inbound слушать на `127.0.0.1:10443` вместо `0.0.0.0:443`:

```json
"inbounds": [
  {
    "listen": "127.0.0.1",
    "port": 10443,
    ...
  }
]
```

```bash
nginx -t
systemctl restart nginx
systemctl restart xray
ufw allow 443/tcp
```

### Исправление 4 — Убрать лишние открытые порты (БЕЗОПАСНОСТЬ)

Сейчас открыты порты 443, 2053, 12345. Порты 2053 и 12345 — нестандартные, подозрительные для ТСПУ.

```bash
# Закрыть нестандартные порты
ufw delete allow 2053/tcp
ufw delete allow 12345/tcp
ufw status

# Все клиенты должны подключаться только на 443
```

## ЧАСТЬ 3: ПРОБЛЕМА ПОСЛЕ 21:00 — ЧЕСТНАЯ ОЦЕНКА

После всех исправлений выше вечерняя проблема может уменьшиться но не исчезнуть полностью. Вот почему и что с этим делать.

**Почему падает именно после 21:00:**

ТСПУ работает в режиме нагрузки. Днём через оборудование идёт пиковый бизнес-трафик — на глубокую инспекцию каждого пакета не хватает мощностей. После 21:00 общая нагрузка на операторские сети снижается — у ТСПУ освобождаются ресурсы для более агрессивной фильтрации. Это подтверждается сотнями одинаковых жалоб на форумах именно с временем отвала 21:00-23:00.

**Что реально помогает по данным форумов:**

Первое — смена SNI (уже в плане выше). Некоторые SNI имеют "белый список" в ТСПУ и проходят даже в жёстком режиме.

Второе — добавить xHTTP как резервный транспорт через Cloudflare CDN. Это единственное надёжное решение для вечерней мобильной блокировки. Трафик идёт через Cloudflare IP который ТСПУ не может заблокировать. Это требует домен и отдельного inbound.

Третье — Fingerprint клиента. В настройках клиента (v2RayTun, v2rayNG) убедиться что fingerprint стоит `chrome` а не `none`. Разные fingerprint дают разные результаты на разных операторах.

**Что НЕ поможет:**

- Перезапуск сервера и Xray — проблема не на вашей стороне
- Смена порта с 443 на другой — только хуже, нестандартный порт режется первым
- Смена UUID клиента — не влияет на ТСПУ-детекцию


## ЧАСТЬ 7: ЕСЛИ НИЧЕГО НЕ ПОМОГАЕТ — ЗАПАСНОЙ ПЛАН

Если после всех исправлений мобильный стабильно не работает на Билайн — это означает что IP сервера (85.137.166.209) или ASN хостера SmartApe попал в усиленный мониторинг ТСПУ.

В этом случае варианты:

**Вариант А:** Добавить второй VPS в другой локации (Финляндия или Нидерланды, другой хостер — Hetzner или Contabo) с тем же конфигом. Направить мобильных пользователей на второй сервер.

**Вариант Б:** Добавить xHTTP inbound через Cloudflare CDN на текущем сервере. IP сервера скрыт за Cloudflare — ТСПУ не может заблокировать по IP. Требует латинский домен + Cloudflare аккаунт (бесплатный).

**Вариант В:** Сменить IP текущего сервера у хостера SmartApe (обычно платная операция ~150-300 руб). Новый IP начинает с чистой истории.
